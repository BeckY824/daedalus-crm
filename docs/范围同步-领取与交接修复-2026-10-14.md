# 范围同步：公海领取 / 业务员交接修复 + 删除残留加固（2026-10-14）

分支 `fix/scoped-claim-handover`（基于 `feat/team-sim-scoped` c0d19bb ← `wip/scoped-sync-handoff` fe8f615）。
相关代码：`src/lib/sync/scope-policy.ts`（推送可写）、`src/lib/tenant/sync-scoped.ts`（收范围推送 / 目录 / 拉取）、
`src/lib/sync/client.ts`（范围推 / 范围一轮）、`src/lib/sync/scoped-local.ts`（记录快照 / 擦净删除残留）、
`src/app/(app)/customers/pool-actions.ts`（领取 / 撤销领取）。

## 1. 问题

**Bug 1：业务员从公海领取，各台分叉。** `领取` 在一个事务里先删 `CustomerPool`、再改 `salesOwnerId`，同步日志按这个顺序推。
服务端 `收范围推送` 逐包按「前面几包落下之后」的状态核 `范围可写`：删公海那一包要求删完之后客户仍归自己（防止把公海客户扯成老板私客），
而此时负责人还没改 → 整批 403。客户端逐条重推：删公海那条单独推仍被拒、转成范围冲突；改负责人那条单独推时客户还在公海、通过。
结果：服务端和其余各台「负责人是他、但仍在公海」，领取的人本机已出公海，各台对不上（五台实测红在这一步）。

**Bug 2：业务员把客户交给同事，接手的人永远收不到。** 改负责人会把客户的 `routeSeq` 推到这一批的编号；非老板只从
「routeSeq 之后的第一份起点快照（SyncScopedBaseline）」开始拉（`给范围拉取`）。交出去的人改完负责人就失权：
事后补发起点 403、客户端跳过并清掉待补（`补发起点`）；接手的人本机没有这位客户、补不了；老板只补自己改的。
同一次交接里跟在转交后面的改动（`patchCustomer` 先改负责人、记操作日志，再把没做完的计划带过去）也全部 403 成冲突。

**连带发现：改归属之后才新建的记录，非老板也收不到。** 例如领到之后老板给这位客户新记一条跟进：这条跟进没有起点、
`给范围拉取` 直接跳过它。

**加固（Bug 3）：清理后库文件里还有删掉的数据。** `清理失权副本` 已开 `secure_delete` 并 checkpoint，但旧协议时期改过的行在
页内空隙 / 空闲页留着旧副本、WAL 里有旧页：五台实测（migrate 模式）业务员 `crm.db` 和 `crm.db-wal` 原始字节里各搜得到 4 位老板私客的电话。

## 2. 根因

服务端把「一次推送」当成互不相关的一串包、逐包按前一包落下后的状态判权；而客户端一个动作（领取、交接）产生的是一组
**本来就在同一个本地事务里**的改动，包的先后只是 SQL 语句的先后。领取 / 交接正是「这组改动做完之后自己失去（或换了）权限」的动作，
逐包判权会在这组改动的中间把自己判成无权。起点快照又只能在失权后单独补，于是交出去的人永远补不了。

## 3. 修法（选定方案）

### 3.1 服务端：一次推送按「请求开始时的权限」核（`scope-policy.ts 推送可写`）

每一包按两种状态各核一次 `范围可写`，任一通过即可：

1. **当前**：本次请求里前面已接受的包落下之后的状态（原规则；本次刚新建 / 刚领到的记录靠它）。
2. **起点视图**：请求开始时已有的记录取开始时的版本；本次请求里新建的记录取它第一次被接受时的那一版。

被拒的包先不落、挪到本次请求末尾再核，直到没有进展（等于把它排到这次请求最后——旧客户端先删公海、后改负责人的领取靠这一步过）。
仍被拒：整批回滚，403 回包带 `denied`（被拒包的下标）。`state` 回包新增 `pushRule: "request-start"`、`maxPackets: 1000`；
一次推送上限 100 → 1000 包（8 MB 不变），好让转交和它的起点快照放进同一次请求。

**安全论证**（为什么不多给权限）：

- 引理：请求开始时**不可读**的已有记录，本次请求里任何一包都不能让它变成可读——改它本身、给它挂公海行、改它的父链，
  都要求它（或它的父记录）先可读，而这些检查在两种状态下都做。所以起点视图里每一条记录，都是这台设备在本次请求某一刻合法可读的版本
  （开始时就可读的，或自己刚新建、建的那一刻已核过的）。
- 因此按起点视图放行的包，换个顺序（排到转交之前）逐包核本来也能过；挪到末尾再核的包，也是按那个位置的状态核的。
  直观地说：一次请求接受的包，都能对应到「这台设备在本次请求某一刻合法拥有的权限」，**不比原规则多给权限**，只是不再要求客户端按特定顺序发
  （这是论证思路，不是形式化证明；单测把能想到的伪造组合都钉住了）。
- **下一次请求**一律按那时的状态重新核：转交出去之后，再改子记录、再推起点、再改回负责人都 403（单测「交接」「伪造」两条）。
- 伪造：抢老板私客、给私客塞公海行、借外键把联系人挂到私客下、把自己的跟进挪进私客、给私客推「起点」——任何顺序、和合法包混在一起都被拒，
  `denied` 只列伪造的那几包、依赖合法新建的子记录不被误伤，整批不落库（单测「伪造」）。
- 不能直接给同事新建客户（从没归过自己）：两种状态下都不可读，照旧被拒。
- 重放：同一 eventId 原样重发只当重复（不落、不改归属，不核权限也不会改任何东西）；同 eventId 换内容 409（原有规则，单测保留）。
- 抢领竞态：两人同时领同一位，SQLite 事务串行，先提交的那次请求被接受；后到的那次请求开始时客户已归别人、不在公海，
  改负责人 / 领取记录 / 删公海 / 起点全被拒，整批回滚，他那台把这几条转成显式冲突、下一轮清掉这位（单测 + 客户端三台测试）。
- 老板永远可写，规则对老板不变。

### 3.2 客户端：转交 / 领取连同起点快照同一次推送（`client.ts 范围推`）

- 服务端声明 `pushRule = request-start` 时：一块改动里有改归属的（改负责人 / 渠道负责人、进出公海、改父链），
  把这些记录当前的起点快照（`记录快照`：本条 + 全部子记录 + 挂在它们上的操作日志——原来漏了操作日志）附在同一次请求里。
  起点事件编号按（设备, 这一块推到哪条）定，回包丢了重推得到同样编号、服务端当重复收下。
- 前 100 条里有改归属的，这一块多带到 300 条，同一个动作里跟在转交后面的改动不被切进下一次请求。
- 起点放不下（超过 1000 包 / 7 MB）或起点包被拒：先只推改动，起点记成待补（由老板那台补，见 3.3）。
- 403 带 `denied`：只把被拒的几条转成显式冲突（不静默丢弃），其余原样重推；没有 `denied`（旧服务端）照旧逐条重推。
- 旧服务端（没有 `pushRule`）：完全照旧（100 条一块、起点事后补）。

### 3.3 老板那台补起点（`sync-scoped.ts 目录里` + `client.ts 范围一轮`）

老板的目录回包新增 `needBaseline`：改过归属、有业务员看得到、在改归属之前有过批次、却还没有改归属之后起点的记录（最多 500 条）。
老板那台拉齐之后对这些记录推起点（老板永远有权写）。覆盖：交出去的是旧版本客户端、起点太大、旧数据里卡住的交接。
只给老板，业务员目录里没有这一项。

### 3.4 改归属之后才新建的记录（`给范围拉取`）

记录在 `routeSeq` 之前没有任何批次 = 整段历史都在改归属之后：不要起点，直接从改归属那一刻起给。仍然不会下发改归属之前的历史。

### 3.5 领取 / 撤销领取的写顺序（`pool-actions.ts`）

领取改成「查到公海那一行 → 改负责人 → 写领取记录 → 删公海那一行（删到 0 行整个回滚 = 已被领走）」；撤销领取改成先放回公海、再还负责人。
新服务端上不靠这个（同一次请求任意顺序都收）；它让这一组改动即使被切进前后两次推送、或连的是还没升级的服务端，也逐包都合法。

### 3.6 删除残留（`scoped-local.ts 擦净删除残留`）

`清理失权副本`（含迁移后的首轮清理、被转走 / 被领走后的清理）删了行、以及 `只留自己的`（退出团队、被移出）之后：
`PRAGMA secure_delete = ON` → `VACUUM`（整库重建，只拷活着的行，空闲页和页内空隙都不带过去）→ `PRAGMA wal_checkpoint(TRUNCATE)`（busy = 0 才算数，最多重试 4 次）。

- 本机服务只有一个 Prisma 连接（`lib/sqlite-url 单连接`），VACUUM 排在别的查询后面执行，不会落在事务里；删除事务已提交后才执行。
- 别的进程（自动备份、只读工具）这会儿开着读事务时 checkpoint 截不了：在 `_sync_cursor` 记一行 `wipe_pending`，下一轮清理先补擦；
  `.team.json` 的 `scoped.cleaned.擦净` 记结果（false = 欠着）。退出团队之后没有下一轮，擦不净只记日志（极少见）。
- VACUUM 会改没有 INTEGER PRIMARY KEY 的表的 rowid：本库只有 `_sync_skip` 没主键，且没有任何地方持久引用 rowid（`清孤儿` 只在同一事务里用）。
- 代价：VACUUM 期间本机库的其它请求排队；几十 MB 的库一两秒，只在「这台失去了某些记录」时发生。

### 3.7 清理失权副本的竞态（五台实测 migrate 模式抓到）

`范围一轮` 是「推完 → 取目录 → 清理 → 拉」。推完到清理之间人还在录（「同步正在写一大批时同一台建 5 位客户」那一步）：
刚建的客户服务端还不知道、不在刚取的目录里，原来会被当成失权删掉——读完待推之前建的转成了冲突，之后建的连同步日志一起删掉，**静默丢数据**。
现在读待推、判失权、转冲突、删除放进同一个事务（本机单连接，这期间别的写排队）；待推里「新建」的记录这一轮不算失权，
下一轮推上去（收下就进目录，被拒就由推送转冲突）；挂在失权记录下的新建（父记录 / 操作日志对象失权）照样转冲突，免得留下外键断头。
单测 `sync-scoped-local`「推完到清理之间刚建…」。

## 4. 考虑过、没选的

- **只靠客户端调顺序**（领取先改负责人、交接先带走计划再改负责人）：每个会改归属的动作都得记住顺序，`recordAudit` 这类事务外的写、
  推送恰好切在两次请求之间都会再坏；起点还是只能事后补、交出去的人补不了。保留了领取的调序作兜底，但不作为修复。
- **转交后给交出去的人一段「补起点许可」**（按时间或次数）：失权后仍能写别人的客户（起点包的字段钟可以伪造得很新、盖掉接手人的改动），扩大了权限，不要。
- **只靠老板那台补起点**：老板电脑不在线时，业务员之间的交接一直到不了。现在作为兜底保留。

## 6. 升级 / 兼容

| 组合 | 结果 |
|---|---|
| 新服务端 + 新客户端 | 领取、交接、刚建就交出去：一次推送全收，接手的人一轮内拿到 |
| 新服务端 + 候选 2–5 客户端（没有本修复） | 领取：同一次推送里先删公海后改负责人，服务端挪到末尾再核 → 收下，不再分叉（领取的人和别人都对）。交接：转交和跟在后面的计划 / 操作日志同一次推送 → 收下；起点事后单独补仍 403 → 由**新版本老板那台**按 `needBaseline` 补，接手的人在老板下一轮之后拿到。被拒时旧客户端不认 `denied`，照旧逐条重推、转冲突（和原来一样）。极少数情况下（领取的两条正好被切在前后两次推送，旧顺序）删公海那一次仍被拒、成冲突。 |
| 旧服务端 + 新客户端 | 客户端看不到 `pushRule`：完全按旧规则推（100 条一块、起点事后补、逐条重推）。领取因为调了顺序在旧服务端上也不再分叉；交接仍有 Bug 2（服务端没修） |
| 同一队里新旧客户端混着 | 包格式（v4 密文、元数据）没变，互相收发不受影响；只是旧客户端做交接时依赖老板那台补起点 |

升级顺序：**服务端 → 老板那台 → 业务员**（和《范围同步启用操作手册》一致）。老板那台升级后，旧数据里已经卡住的交接（routeSeq 之后没有起点的记录）
会在老板第一轮同步时被列进 `needBaseline` 自动补上，接手的人随后拉到。原来卡成冲突的那几条（`_sync_scope_conflict`）不会自动重推，仍需人核对。

## 7. 操作手册要补的

- 升级顺序：服务端 → 老板那台 → 业务员。升级后核对：老板那台 `设置 → 团队` 无报错；业务员领公海客户后，其他人一轮内看到「负责人是他、出了公海」；
  业务员交给同事后，接手的人一轮内看到客户、计划、跟进，交出去的人那边没了且没有新增冲突。老板电脑长期不在线的团队，旧版本业务员之间的交接要等老板那台上线。
- 业务员电脑隐私核对（原第 3 节）新增一条：用老板私客 / 已转走客户的电话在 `crm.db`、`crm.db-wal` **原始字节**里搜（`grep -a -c <电话> crm.db crm.db-wal`）应为 0；
  `.team.json` 的 `scoped.cleaned.擦净` 为 `false` 表示 WAL 被占用、下一轮会补擦。
- **备份按设计保留**、不会被清理：业务员电脑 `backups/` 里的每日备份（留 7 份）、升级前备份（留 3 份）、恢复前备份（留 3 份），
  如果是在旧协议时期（每台都有全队数据）或失权之前做的，**里面有当时的全队 / 失权客户数据**，按保留份数轮换掉之前一直在；
  老板电脑的 `backups/before-scoped-sync-migration.db` 是迁移前全量。需要立即清除的（例如员工离职交回电脑），由人手工删除这些备份文件，并告知用户。
- AI 对话里提到失权客户的内容不删（`清理.AI残留` 只计数），同上由人处理。

## 8. 剩余风险 / 没做的

- **起点可能略旧**：交出去 / 领取的人附的起点是他本机当时的状态。如果第三台（通常是老板）在他上次拉取之后、他推转交之前改了同一位客户，
  接手的人拿到的起点里缺这一改（字段钟比较，下一次有人改这一格就会对上）。窗口是一轮同步（约 8 秒）；没有在服务端校验起点是否最新。
- **旧客户端 + 新服务端、领取两条恰好被切在前后两次推送**：删公海那次仍被拒、成冲突（极少见；新客户端没有这个问题）。
- **起点过大**（超过 1000 包 / 7 MB，例如几百条跟进的大客户）不跟转交同一次推送，接手的人要等老板那台补；老板长期离线则一直等。
- **VACUUM 的代价**：清理删了行之后整库重建，期间本机库的其它请求排队（几十 MB 一两秒）；只在这台失去记录时发生。擦不净（WAL 被别的进程长时间占着）时下一轮补擦；
  退出团队之后没有下一轮，只记日志。备份文件、AI 对话里的旧内容按设计不删（见第 7 节）。
- 旧数据里已经转成冲突的领取 / 交接改动不会自动重推，需要人在「设置 → 团队」里核对。

## 9. 追加（候选 6 实机）：同一账号的第二台收不到删除

**现象**：业务员 S 两台电脑（W、M）。客户 C 在公海、两台都有 C 和它的公海那一行。W 领取后，老板和云端都对
（`CustomerPool:C` deleted=1、`Customer:C` 归 S、routeSeq 70；`Customer:C` / `CustomerClaim:C` 有 72–76 的起点，`CustomerPool:C` 只有迁移时的 23）。
M 拉齐了（游标 82、revision 70、无报错），负责人也变成 S，**但公海那一行还在**，C 一直挂在公海页签。

**根因（已用单测复现确认）**：`给范围拉取` 对改过归属的记录，非老板只从「routeSeq 之后的第一份起点」开始给。
`CustomerPool:C` 的 threshold = 客户的 routeSeq 70；起点快照只拍活着的行，删掉的公海那一行永远没有起点；它在 70 之前又有批次 →
整条记录被跳过，删除包永远不下发。已经持有这一行的读者（同一账号的另一台；撤销领取 / 交接 / 删除后，仍有权的其他设备）就一直留着旧行。
同类：任何「改归属之后已被删除、又没有新起点」的记录（例如交接前删掉的跟进、改负责人后删掉的子记录）。

**修法**：
1. 服务端 `给范围拉取`：已删除、没有改归属之后起点、改归属前有批次的记录，**只给把它删成现在这样的那一包**
   （`o = D`、字段钟等于索引里的当前钟、没有归属字段；不论这一包在 threshold 前后，例如旧顺序领取里删公海在改负责人之前）。
2. 接收端 `验收范围包`：删除包里的整行必须为空、改动列必须为空，否则当坏包跳过。
3. 客户端 `照目录补删除`（每轮拉完之后）：目录里标着已删除、本机还有这一行、本机也没有待推改动的记录，按目录里的字段钟补一次删除
   （当回放执行，不进推送队列；本机这一行有更晚的字段钟就不删）。用来修已经卡住的设备（游标早已越过删除包，例如 M）以及旧服务端。

**安全**：删除包的元数据只有表名、编号、字段钟（目录里本来就给这些）；正常客户端发的删除包密文里整行为 NULL（触发器只记 NULL），
接收端再强制核一遍，夹带内容的直接拒收，所以拿到删除包不会看到任何失权期间的历史内容。下发的只是「当前那一次删除」，不是历史批次。
`照目录补删除` 只用目录信息，不解密任何东西。别的业务员（看不到的范围）照旧 403。

**测试**：
- `tests/sync-scoped-start-rights.test.ts` 新增：同一账号从头拉 `Customer:pool-a`，收到且只收到删公海那一包，解开后 `r = null`；
  交接前删掉的跟进，接手的人只拿到删除、拿不到删之前的内容；wang 照旧 403。在修之前的服务端上这一条红。
- `tests/sync-scoped-second-device.test.ts`（新，四台真实客户端：老板、li、li 的第二台、zhao，9 条）：第一台领取 / 撤销领取 / 第二台领取 /
  交出去（第二台也清掉、字节不留）/ 别人交给 li 和老板分给 li（两台都收到）/ 放公海 / 删跟进删客户 / 已卡住设备照目录补删除 / 夹带内容的删除包被拒。
  在修之前的代码上 9 条里 5 条红（第一条就是实机现象）。
- 五台实测新增「同一账号的第二台电脑」一步（见 `scripts/team-sim/README.md`），三种模式都跑。

**升级**：服务端修好后，新卡住的不会再出现（任何版本的客户端都能收到删除包）；**已经卡住的设备**（游标已越过删除包）要升级到带
`照目录补删除` 的客户端才会自愈；没升级的可以让老板把那位客户再放进公海 / 领一次，或者重装后重拉。

**安全复查两条 low（2026-10-14）**：
- 回放（含照目录补删除）原来在事务外先编本机字段钟，编完到开事务之间人又写的一笔（例如撤销领取把公海那一行放回来）没有字段钟，会被更早的删除删掉、而它的插入照样推出去。
  现在字段钟在回放事务里编（本机单连接，中间插不进写），语义不变。单测用夹在 `$transaction` 前写一笔的代理复现，修之前红。
- 删除包原来按记录回看最近 50 批；删除之后又来 60 条更早字段钟的改动就找不到了，而且每次拉取每条都多一次查询。
  现在收下一包「成了当前状态的删除」时把批次号记进索引（`delSeq`），拉取直接用；之前建的索引没有 delSeq，才按记录分页找（不设固定条数）。
  只给当前那一次删除、删除包不带内容，读不漏的保证不变。单测：删除后 60 条更早改动，带 / 不带 delSeq 都只拿到删除包，修之前红。

## 10. 追加（候选 7 Windows CI）：「公海」那条单测 20 秒超时

- 现象：`tests/sync-local.test.ts` 的「公海：甲放进去、乙领走…」在 Windows 上 20 秒超时，紧接着那条也拖到 17 秒；Mac 上两边都是零点几秒。
- 判断：这条只走 `local.ts`（改身份 / 触发器 / 待推 / 回放），候选 6→7 的改动不在它的路径上（照目录补删除、删除包、擦净都不经过这里）。
  同一轮 Windows 里别的测试文件也忽快忽慢两三倍。测试库拷贝原来是 Prisma 默认样子：连接池多个连接、delete 日志模式（每次提交新建再删
  `-journal`）、每次提交刷盘——Windows 上杀毒扫新文件、删文件时占着、磁盘刷盘抖动，几十次提交就能拖过 20 秒；超时那条的后半截还在跑，
  又拖慢下一条。把握中等：拿不到 Windows 机器复现，是按日志和代码推的。
- 修：
  - 测试库拷贝和桌面端正式库一样：1 个连接、WAL + synchronous=NORMAL；每步限时 12 秒，卡住报出卡在哪一步；超时那条的后半截碰不到下一条的库。
  - 擦净删除残留（产品代码）：别的程序拿着读快照时原来单连接最坏卡 23 秒（新测试实测）；现在等锁 1 秒、总预算 5 秒，等不到记欠擦下一轮补，
    连接原来的等锁时长恢复。Mac / Linux 没人占锁时一次就过。
  - 拉取：云端回「还有」却一批不给时停下，不再空转；换过钥匙 409 重推最多 3 次。
- 没做：别的同步测试（sync-client、sync-scoped-* 等）的拷贝库也还是默认连接池 / delete 日志模式，Windows 上同样可能偶发慢；这次只改了出事的那个文件。
