# 范围同步（CRM_SCOPED_SYNC）启用操作手册

> 本手册只描述步骤，**本分支不修改任何生产配置**。每一步须由运维/负责人人工执行并记录。
> 相关代码：`src/lib/tenant/sync-scoped.ts`、`src/app/api/sync/scoped/route.ts`、`src/lib/sync/client.ts`；控制面迁移 `control-migrations/019-scoped-sync.sql`、`020-scoped-sync-baseline.sql`（只加表）。

## 0. 前提

- 新候选桌面端（含范围同步客户端）已通过 Windows 整包、Mac 原生验证，并已发给**所有**团队成员；旧客户端在开启后会被拒（409，提示升级）。
- 服务端镜像已包含 019、020 迁移；entrypoint 每次启动会按顺序重跑 `control-migrations/*.sql`（只加表、IF NOT EXISTS）。
- 先在测试服务器、合成团队上完整走一遍本手册，再上生产。

## 1. 预先备份（必须）

1. 停写或选低峰；记录当前镜像版本和 compose 文件。
2. 备份控制库（SQLite，`CONTROL_DATABASE_URL` 指向的文件）：
   `sqlite3 <control.db> ".backup '<备份目录>/control-before-scoped-sync-YYYYMMDD.db'"`
3. 备份同步密文目录（`SYNC_DIR`，默认 `WORKSPACE_DIR/sync`），例如 `tar czf sync-before-scoped-sync-YYYYMMDD.tgz <SYNC_DIR>`。
4. 校验备份：`sqlite3 <备份>.db "PRAGMA integrity_check;"` 返回 `ok`；记录 `SELECT COUNT(*) FROM SyncBatch;`。

## 2. 分阶段顺序

1. **部署新镜像，开关保持关闭**（不设 `CRM_SCOPED_SYNC`）。验证：
   - `SELECT name FROM sqlite_master WHERE name IN ('SyncPrivacy','SyncScopedRecord','SyncScopedBatch','SyncScopedBaseline');` 四张表都在；
   - 旧团队照常同步；`POST /api/sync/scoped {action:"push"}` 返回 404。
2. **服务端开启**：在 compose 的 environment 中加入 `CRM_SCOPED_SYNC: "1"`（这一步是生产配置变更，需单独审批），重启。
   - 开启后：未迁移团队的**业务员**旧接口立即返回 409（不能再收全队包），老板旧接口仍可用，直到老板迁移。所以第 3 步要紧接着做。
3. **逐个团队，老板先迁移**：在老板「建团队的那台」电脑上，以环境变量 `CRM_SCOPED_SYNC=1` 启动新桌面端，点「立即同步」。
   - 客户端顺序：本机备份 → 推完旧改动并拉齐 → 冻结旧流 → 追到冻结点 → 推送完整起点（可断点续）→ 提交。
4. **业务员升级**：各业务员打开新版本，正常同步即可（不需要环境变量）。

## 3. 每步验证

- 老板迁移后（控制库）：
  - `SELECT stage FROM SyncPrivacy WHERE teamId='<团队>';` 为 `ready`；
  - `SELECT COUNT(*) FROM SyncScopedBatch WHERE teamId='<团队>';` > 0；
  - `SyncScopedRecord.metadata` 中搜不到任何客户姓名、电话（只应有编号、负责人、字段钟）。
- 老板电脑：`backups/before-scoped-sync-migration.db` 存在；`scoped-sync-migration-baseline.json` 已删除；设置 → 团队无报错。
- 业务员电脑：
  - 只读打开 `crm.db`，`SELECT COUNT(*) FROM Customer WHERE salesOwnerId <> 'acct_<本人>' AND channelOwnerId IS NOT 'acct_<本人>' AND id NOT IN (SELECT customerId FROM CustomerPool);` 为 0；
  - 用老板私客的姓名/电话在全库（含 `_sync_log`、`ImportRow`）搜索为 0；
  - 首页客户数与迁移前界面一致；本人离线改动仍在；如有冲突，设置 → 团队可见并可导出。
- 交叉：业务员伪造老板私客编号推送 → 403；旧版本客户端 → 409 提示升级。
- 业务员电脑**库文件字节**（2026-10-14 起）：`grep -a -c <老板私客电话> crm.db crm.db-wal` 均为 0（清理失权副本后会整库重建、截断 WAL）；
  `.team.json` 里 `scoped.cleaned.擦净` 为 `false` 表示 WAL 被别的程序占着、下一轮补擦。
- 领取 / 交接（2026-10-14 修复后）：业务员领公海客户后，老板和其他业务员一轮内看到「负责人是他、出了公海」；业务员交给同事后，接手的人一轮内看到客户和计划、交出去的人那边没了且无冲突。
  候选 2–5 的旧客户端做交接时，起点由**已升级的老板那台**补（老板下一轮之后接手的人才看到）——所以升级顺序是服务端 → 老板 → 业务员。
  详见 `docs/范围同步-领取与交接修复-2026-10-14.md`。
- 备份：业务员电脑 `backups/` 里的每日 / 升级前 / 恢复前备份，若做于旧协议时期或失权之前，**含当时的全队 / 失权客户数据**（按保留份数轮换），清理不会删它们；需要立即清除时由人手工删除并告知用户。

## 4. 回滚

按影响由小到大：

1. **某团队迁移卡住（stage=building）**：先看老板端报错，通常重试即可续做。不要手改 SyncPrivacy。
2. **整体回退开关**：去掉 `CRM_SCOPED_SYNC` 并重启。注意：已有 SyncPrivacy 行的团队**仍走新协议**（设计如此，防止退回全队包）；未迁移团队恢复旧协议。
3. **必须让某团队退回旧协议**（仅在新协议有严重缺陷时，需负责人批准）：
   - 停服务 → 用第 1 节备份恢复控制库**或**仅删除该团队行：`DELETE FROM SyncPrivacy WHERE teamId=?; DELETE FROM SyncScopedRecord WHERE teamId=?; DELETE FROM SyncScopedBatch WHERE teamId=?; DELETE FROM SyncScopedBaseline WHERE teamId=?;` → 启动；
   - 旧 SyncBatch 未被修改，旧协议可从原游标继续；但业务员电脑已清理的数据会由旧协议重新下发全队包（隐私回退），须告知用户；
   - 老板电脑如需回到迁移前状态，用 `backups/before-scoped-sync-migration.db` 恢复。
4. **镜像回退**：恢复旧镜像前先回退开关；019/020 只加了表，旧镜像可忽略这些表。

## 5. 记录

每个团队记录：迁移时间、老板设备、SyncScopedBatch 条数、业务员验证结果、冲突条数。异常连同老板端/业务员端 `logs/app.log`、`logs/server.log` 一并保存。
