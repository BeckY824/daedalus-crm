# 团队版五台实测（`npm run test:team`）

一条命令把桌面端团队版从注册到移除成员走一遍，每一步都有断言（2026-10-04，上线前测试 4.1）。
单测只有一台真客户端，这里是 6 个真进程：一个本机云端（托管模式 + 中转）+ 5 台桌面端本地服务（和 Electron 里跑的同一个 `desktop/server-bundle`），每台配一个模拟壳，照真壳前台的节奏每 8 秒戳一次 `/api/desktop/sync`。

## 怎么跑

```bash
npm run test:team
```

- **要多久**：约 2–2.5 分钟（本机 M 系列，2026-10-04 加了 4.3 / 4.5 之后实测 128–151 秒）。`desktop/server-bundle` 比 `src/`、`prisma/`、`migrations/` 旧（或还没有）时会先自动 `cd desktop && npm run build:server`（含 `next build`），再加 1 分钟左右。
- **端口**：云端 3520，5 台 3521–3525。被占了就 `TEAM_SIM_PORT=3620 npm run test:team`。
- **数据**：全在系统临时目录 `team-sim-*` 里（各台自己的 crm.db / .cloud.json / .team.json，云端的 control.db / sync），跑完不管红绿都按进程号关掉起过的进程、删掉临时目录。要留现场看完整日志和库：`TEAM_SIM_KEEP=1`。
- 其它开关：`TEAM_SIM_SEED`（老板先录几位客户，默认 30）、`TEAM_SIM_BUILD=1` 强制重新装配 / `=0` 不管新旧直接用现有产物。
- **范围同步**（`CRM_SCOPED_SYNC`，2026-10-13）：`TEAM_SIM_SCOPED=1`（或 `npm run test:team:scoped`）、`TEAM_SIM_SCOPED=migrate`（或 `npm run test:team:migrate`），见下面「范围同步模式」。不设就是旧协议，和以前一模一样（子进程显式拿到空的 `CRM_SCOPED_SYNC`，外面 shell 里留着的不会混进来）。

## 断言了什么（超时就红）

下面是旧协议（全队包）模式；范围同步模式改了哪些见后面一节。

1. 5 个云端账号注册、登录拿设备令牌（每人一个 `x-forwarded-for`，绕开同 IP 一天 3 个的上限）；**zhao 那台是 v0.46.14 的老库**（老版本 schema + 老迁移 + 管理员名下 2 位老客户，起服务时按当前迁移升级，上线前测试 4.5）；各台自动登录、选模版
2. 老板先录 30 位客户 / 60 条跟进 → 建团队 → 运营台开通 → 等老板那台把老数据推上云（真实情况开通是人工的、分钟级，同事加入时老数据早在云上）→ 4 人凭邀请码加入，成员名单和角色对
3. **最后一位加入后 15 秒内** 5 台客户数、跟进数、团队账号数一致（含老库带进来的老客户和老跟进）；每台本机角色对（老板 ADMIN、业务员 SALES）；老库的老客户在每台都归 zhao、老板和 zhao 看得到、别的业务员看不到
4. 4 位业务员各写一位客户 + 一条跟进 → **老板 10 秒内**在客户列表和客户页上看到
5. 业务员 A 的客户列表、跟进页、直接打开客户页都看不到业务员 B 的客户（先确认 B 的客户已经同步进 A 的库，才算数）
6. 同一位客户：两台同时改不同字段两边都留；同一字段两台几乎同时改，后改的赢（来回各一次）
7. 老板放一位进公海 → 业务员在公海页看到 → 领取 → 其余各台负责人变成他、出了公海
8. （4.3 可见性变化）业务员把自己的客户放进公海 → 同事和老板在公海看到 → 另一位领走 → 原来那位列表和客户页都看不到了
9. 交接带活：业务员在客户页把负责人改成同事 → 没做完的计划跟着过去，接手的人计划页里有、交出去的人看不到客户和计划
10. 老板批量换负责人：A 的客户转给 B → B 看得到（带着原来的跟进），A 看不到
11. 业务员自己退出团队：他那台只留自己的（含老库带进来的）、别人那边一条不少、收不到他退出之后写的、老板的成员名单里没他了
12. （4.5 混合）离线一段时间回来：li 那台本地服务按进程号关掉，老板录 3 位、改他名下一位的备注，再开机 → 一轮内补齐、客户页上看得到新备注
13. 中转断了再连上：云端按进程号关掉，老板和业务员照常写 / 改，确认互相收不到；同一个数据目录和密钥重起云端 → 各台补齐
14. 老板移除一人 → 其余各台自动换钥匙（钥匙编号变大）并继续收到新数据；被移出那台自动退出团队、只剩自己的客户、收不到新数据，他那台的清理没有传给别人

## 范围同步模式（`TEAM_SIM_SCOPED`）

```bash
TEAM_SIM_SCOPED=1 TEAM_SIM_PORT=3730 npm run test:team        # 新团队一开始就按范围同步
TEAM_SIM_SCOPED=migrate TEAM_SIM_PORT=3740 npm run test:team  # 旧协议的老团队 → 开开关 → 老板迁移
```

- `1`：云端和 5 台本地服务都带 `CRM_SCOPED_SYNC=1`。开关开着时新团队没有单独入口：老板那台开通后的第一轮看到「开关开、我是老板、还是 legacy」就走老板迁移（备份 → 冻结旧流 → 推起点 → commit），控制库 `SyncPrivacy` 变 `ready` 之后业务员才进得来。
- `migrate`：第 1–11 步照旧协议跑（每台都有全队数据），然后**一步**：同一数据目录、同一密钥带开关重起云端 → 重起老板那台、等迁移完成（控制库 `SyncPrivacy = ready`、`.team.json scoped.stage = ready`、`backups/before-scoped-sync-migration.db` 在、`scoped-sync-migration-baseline.json` 删了、老板客户 / 跟进数不变）→ 重起 4 位业务员 → 各台清掉失权副本（`scoped.cleaned.删 > 0`、客户只剩自己的、同事的客户没了、自己的还看得到）。之后的步骤全按范围断言（迁移后继续同步就是靠它们证明的）。
- 不能和 `TEAM_SIM_OLD_BUNDLE` 一起用（旧版本客户端开了开关会被 409 拒掉）。

**按范围改了的断言**（每台该有什么以老板那台为准——老板收全队）：

| 步骤 | 旧协议 | 范围同步 |
|---|---|---|
| 建团队开通 | 老板那台老数据推上云 | 老板那台完成范围迁移：`SyncPrivacy = ready`、`SyncScopedBatch ≥ 种子数`、备份在、起点文件删了 |
| 加入后对齐 | 5 台都是 32 位 / 62 条跟进 | 老板 32 / 62；zhao（老库）只有自己的 2 / 2；wang / li / sun 0 / 0；成员账号都是 5；业务员 `.team.json` 范围阶段 ready、没有 lastError；老库的老客户只在老板和 zhao 那台 |
| A 看不到 B | 先等 B 的客户进 A 的库，再看页面 | 各台跑完一轮之后 A 的库里**根本没有** B 的客户和老板的私客，页面也没有 |
| 同时改同一位 | 5 台一致 | 老板、wang 一致；li / zhao / sun 跑完一轮库里没有 |
| 老板放进公海 → li 领 | 别人那边负责人变 li | **业务员加入之后**老板才放进公海的这位，4 位业务员库里都收到（带 2 条跟进、在公海）；li 领走后 wang / zhao / sun 库里连跟进一起清掉，老板那边负责人 li、出了公海 |
| wang 放公海 → zhao 领 | wang 看不到 | 另外 wang / li / sun 库里清掉 |
| 交接带活 li → zhao | 计划跟着过去 | 另外 zhao 库里有跟进；li 库里客户 / 跟进 / 计划一行不剩；wang / sun 收不到 |
| 老板批量改负责人 li → wang | wang 看得到带跟进 | 另外 wang 库里有跟进；li 库里清掉；zhao / sun 收不到 |
| 外贸档案 / 订单 | 档案 5 台一致；订单同步进 li 的库 | 档案只在老板、wang；li / zhao / sun 跑完一轮库里没有档案和订单 |
| 带订单交接 wang → li | li 订单一览有 | 另外 li 库里订单、档案都在；wang 库里客户 / 档案 / 签约 / 订单清掉 |
| zhao 退出 | 他的老客户留在每台 | 只留在老板那台（别的业务员从来没有） |
| li 离线回来 | 补拉关机时老板录的 3 位 | 老板这 3 位是私客、补拉时也不来；另分给 li 1 位（带跟进）要补到 |
| 中转断了再连上 | 各台互相补齐 | 老板收到王写的和王改的；王只有自己的；老板断线时改 sun 名下一格、连上后 sun 补到；跑完一轮之后不该有的一位也没来 |
| 同步时写一大批 | li 收老板的 40 位 | 这 40 位由老板直接分给 li（同样往 li 库里写一大批）；li 同时录的 5 位只传到老板 |
| 移除 sun | 老板、wang、li 都收移除后的新数据 | 老板这位分给 li：老板两位都有、wang 只有自己写的、li 只有分给他的；各台客户数按各自的应增；sun 录的客户只留在老板那台 |

**越权检查**（`scope-check.mjs`，只读打开业务员那台的 crm.db；读库看得到 WAL 里的内容）：业务表里每一行都按 `src/lib/sync/scope-policy.ts` 的 `范围父表` 一路找到客户（父表和同步表是跑的时候用 tsx 从源码读的，不抄一份），客户必须是老板那台上「负责人 / 渠道负责人是他，或在公海」；待归属联系人、没挂客户的线索、对象不认得的操作日志必须是他本人的；User / Setting / Channel / Supplier 全队共享不查。`_sync_log` / `_sync_field` / `_sync_tomb` / `_sync_skip` 里按（表, 编号）记的副本、`ImportRow` 一样核；再拿所有不该有的客户的电话和名字在 `_sync_log` 整行、`AuditLog` 说明 / 明细、`ImportRow.before` 里全文搜。`_sync_scope_conflict`（失权前没传上去的本人改动，产品有意保留）不算。每台最多等两轮壳清干净，不干净就红并列出越权的行。检查点：初次加入、各自录客户之后、老板放进公海、业务员领取、业务员放公海 / 同事领走、交接、老板批量改负责人、带订单交接、业务员退出（走的人只按「本人」核，公海的也不该带走；留下的照旧）、老板移除（同上）；migrate 模式迁移完再查一次。

**只观察不判红**：库文件（`crm.db`、`crm.db-wal`）原始字节里还搜得到不该有的客户的电话（SQL 查不到，只在空闲页 / 页内空隙里）——迁移后和移除那一步之后各看一次，列在「观察」里。

步数：`1` 和旧协议一样 27 步，`migrate` 多迁移那一步共 28 步。

**2026-10-13 现状：两种范围模式都红在「老板放一位进公海 → 业务员领」**，是产品问题不是脚本：领取（`pool-actions.ts` 领取）在一个事务里先删公海那一行、再改负责人，同步日志按这个顺序推；服务端逐条核写权限（`sync-scoped.ts` 收范围推送 → `scope-policy.ts` 范围可写），删公海那一条核的是「删完之后客户还归老板、不在公海」→ 业务员读不到 → 403，客户端把它转成范围冲突。结果负责人改过去了，公海那一行在老板和别的业务员那里一直留着。另外实验（本机临时改成先改负责人、后删公海，没提交）跑过这一步之后，「交接带活」又红：业务员把客户交出去后自己已经无权补发起点（补发起点 403 就跳过、并把待补清掉），接手的人永远拉不到这位客户。修好之前别为了绿去改这两步的断言。

没测的：**新旧客户端混在一个队**（要另装一份老版本的 server-bundle，老版本还没有团队同步——0.46.15 是第一个带团队版的版本，眼下不存在「老客户端进团队」这种组合），等下一个带同步改动的版本再加。

动作都走 HTTP：改数据调的是界面按钮背后的同一个 Server Action（从构建产物的 `server-reference-manifest.json` 按「文件 + 导出名」找编号，清单在 `actions.mjs`，`tests/team-sim-actions.test.ts` 在平常的 vitest 里钉着它们还在），「看得到 / 看不到」看的是那台的页面。只有「每台都有全队数据」这类界面上本来就看不到的事才只读打开库核对。

红了会打印：哪一步、哪台、期望、实际，以及那台模拟壳最近几轮的同步结果、`.team.json` 里的 lastError、本地服务和云端的日志尾巴。
同步没成但下一轮补上的轮次不判红，跑完列在「观察」里。等待类断言超时后会再看 20 秒，红的时候分得清是「慢了，第几秒才到」还是「根本没到」。

**已知偶发红**（约十来次一次）：「业务员在公海里看到（10 秒内）」这类 10 秒断言报「慢了」。原因在产品里不在脚本：写库正赶上本机一轮同步在跑时，「改完 1.5 秒就推」会被吞掉（lib/team-scope.ts 改完推一下 遇到 __同步中 直接返回；计时到点时上一轮没跑完，同步一轮() 直接复用那一轮），改动要等壳的下一轮才推，同事最长约 16 秒才看到。修好之前别把 10 秒放宽。
